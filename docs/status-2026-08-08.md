## 1. One-paragraph summary

**agent-trail** is an MIT-licensed kanban board that orchestrates Claude Code on real
projects: drop a PRD → task graph → agents execute in worktrees with live telemetry →
humans get pinged for decisions. Phases 1–5 are shipped and tagged `v1.0.0`. Since
2026-07-28 all work has been on one thing: the **knowledge layer** — a shared team-memory
substrate whose thesis is that every other team-memory product asks people to *write down*
what they know, while agent-trail already watches them do the work, so the knowledge
writes itself and every teammate's agent inherits it.

**The honest headline:** the single-machine loop is genuinely closed and working
end-to-end. The multiplayer half — the part the entire pitch and pricing model rest on —
is at zero.

### 2.2 What actually works today

The write side and the read side both fire on every spawn. A downstream task now inherits,
without opening a single file:

- the exact typed signatures its upstream task produced (capability contract, §4.2b);
- the conventions and rulings governing that module (L0 constitution fold, §4.2);
- the top-3 semantically related facts from the whole team log (FTS5 retrieval, §4.3);
- warnings about prior failed attempts on the files it is about to touch (§4.5).

That is roughly **3,000 LOC across 12 files in `packages/core/src/knowledge/`**, with 72+
dedicated tests. The thesis is demonstrably real on one machine.

### 2.5 Two things that quietly undercut what already shipped

1. **No staleness derivation (§4.2e).** The contracts just built will confidently hand a
   downstream task signatures that no longer exist after any rebase, revert, dependabot
   bump, or teammate edit made outside agent-trail. The doc is explicit that this
   assumption fails on every real team.
2. **No cache breakpoints (§4.4).** The token-savings number is the headline marketing
   claim, and right now it is not measurable — let alone proven.

## 3. Where we're moving

Ordered by leverage, not by doc order.

### Next — §4.4 three-band prompt + cache breakpoints

The doc's own highest-leverage item, and mostly a *reordering* of code that already exists.
Split prompt assembly into Band A (org prefix) / Band B (project prefix) / Band C (task
pack) / Band D (governance), place explicit `cache_control` breakpoints after A and B, and
persist `cache_read_input_tokens` separately so cache-hit-rate becomes a real bench metric
— today it is parsed but folded into `totalInputTokens` and lost.

Two things to verify empirically before any of it goes into marketing copy:
- Anthropic caches are isolated per org and (since Feb 2026) per workspace, so
  cross-teammate cache sharing requires a shared org API key, not per-user `claude login`.
- Bands A+B must clear the minimum cacheable prefix length or the breakpoint is a no-op.

**Unlocks:** a defensible number for the benchmark and the Show HN post.

### Then — §4.2e git validity oracle

Small, and it protects the contract work from being wrong in the way that erodes trust
fastest. Anchor contracts to `base_sha`, compute `signature_hash`, derive staleness at pack
time by comparison, add a `post-merge` hook, and degrade gracefully for commits agent-trail
did not author.

**Unlocks:** contracts stay honest as the repo moves underneath them.

### Then — §4.6 relay + cursor sync

`POST /v1/events`, `GET /v1/events?since=`, `GET /v1/events/stream?since=`, plus an outbox
on the local SQLite mirror. The protocol itself is ~150 lines; the real cost is the
workspace model and auth around it (better-auth + GitHub OAuth, Neon + Drizzle).

Explicitly **not** adopting ElectricSQL / PowerSync / Zero / LiveStore or any CRDT library —
an append-only log needs a cursor, not a sync engine.

**Unlocks:** everything multiplayer. Presence, live session join, shared steering, the
decision inbox, cross-machine handoff — all of it is behind this, including the YC demo
video and the entire Team Cloud tier.

### After that

- **§4.2c symbol index** — `symbols` table + `find_symbol` / `get_signature` / `who_calls`
  MCP tools, replacing the `repo-map.ts` term-overlap ranker. The pull half matters more
  than the push half: ~50 tokens per lookup instead of a 5k-token file read.
- **§4.2d code graph** — `graph_nodes` / `graph_edges` in Postgres (not Neo4j), joined to
  the knowledge graph by `governs` edges.
- **§4.3 vector half** — fastembed / nomic-embed-text 256d Matryoshka + kNN + RRF fusion +
  the full scoring formula, then graph expand.
- **§4.2b LLM intent pass** — one Haiku call per task to fill `invariants` and
  `deliberatelyNotDone`; swap the regex extractor for tree-sitter.
- **§5.3 seeded-corpus A/B** — the controlled benchmark against dump-mode.
- **§4.2 module briefs + PROJECT_MAP** projections.
- **§3.4 `state.json` LWW fix** — tracked separately; must not block the knowledge layer.

## 5. The risk that matters

§7.1 ranks it first and nothing has changed: **building for months and never launching.**
Eleven prior plan docs, ~38k LOC, v1.0.0 tagged 2026-07-05, launch scheduled 2026-07-07 —
and the repo still has no distribution. Distribution, not build, is the bottleneck.

Two gates exist specifically to counter this: the Week 0 launch-debt gate (overridden) and
the Week 10 gate — *don't launch until ≥2 non-Nish teams have run a real task through a
shared board.* The Show HN date must be immovable.

The sequencing above is chosen with that in mind: §4.4 produces the number the launch post
needs, and §4.6 produces the demo. Neither is worth doing twice.
